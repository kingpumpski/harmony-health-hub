## Findings and disposition

1. All 21 groups contain different file contents; the SHA-256 values are distinct within each group. This is not a set of duplicate byte-identical migrations.
2. The SQL signatures show materially different feature and security domains in every collision group. Several timestamps pair unrelated schema changes; others pair distinct permission hardening operations. Applying both in an arbitrary order can affect object existence, grants, function signatures, RLS policies, and trigger state.
3. The fingerprints make archive-level candidate identification reproducible, but they do not supply source provenance or prove deployment state. A filename rename alone would create a new pending migration identity in environments that recorded only one of the colliding versions.
4. No file was renamed, deleted, reordered, promoted, or applied as a result of this audit. The forward-only validator and 21-group preflight remain unchanged.

## Required evidence before a collision decision

For each candidate, collect: (a) original Git blob/commit or trusted archive provenance; (b) exact hosted ledger version/name identity and any environment-specific ledger evidence; (c) live catalog/function/policy state relevant to the candidate; (d) dependency ordering and idempotency analysis; and (e) a disposable PostgreSQL replay using the selected authoritative history. Where evidence is unavailable, preserve the collision as unresolved and design a separately versioned fresh-environment bootstrap rather than impersonating an applied historical migration.

The supplied ZIP's hash inventory is an evidence aid, not authorization to alter the canonical database.
